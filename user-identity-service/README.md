# user-identity-service

Human identity and authentication orchestration module for the `bank-iot-platform`.

## Purpose

This service answers **"who is the human?"** and produces a short-lived, auditable authentication context. It deliberately does **not** own CID/DID, application/device attestation, JWT signing, MQTT sessions, or authorization.

### Boundary

```text
Flutter/Web client
       |
       +--------------------+
       |                    |
       v                    v
client-identity-service   user-identity-service
 CID/DID/attestation      OTP/PIN/biometric/authentication
       |                    |
       +---------+----------+
                 v
        authentication context
                 |
                 v
           token-service
       access/refresh/JWT/JWKS
```

The service is designed around **authentication transactions**, **assurance levels**, **pluggable providers**, and **step-up authentication** so additional methods can be added without changing the core flow.

## Implemented in this module

- User identity record and status
- Authentication transaction lifecycle
- OTP challenge, hashing, expiry, retry/lockout and purpose binding
- Pluggable OTP delivery provider with a safe logging/mock implementation
- Pluggable biometric provider with mock provider for development/testing
- Device-biometric assertion abstraction for future Android/iOS/TEE/passkey integration
- Assurance levels `IAL-0` through `IAL-4`
- Authentication methods: OTP, PIN, PASSWORD, BIOMETRIC, DEVICE_SIGNATURE, PASSKEY
- Authentication policy engine for login and high-value/step-up scenarios
- Step-up authentication
- Replay protection through one-time transaction/challenge state
- Redis-backed short-lived state/rate limits
- Oracle-backed durable identity, authenticator and audit records
- Internal token-service verification endpoint
- Security/audit events persisted to Oracle
- Actuator health/info/metrics endpoints
- Validation and global API error model
- Mock providers suitable for client simulator integration

## Assurance levels

| Level | Meaning | Typical evidence |
|---|---|---|
| IAL-0 | UNKNOWN | no verified human identity |
| IAL-1 | BASIC | low-risk/basic identity assertion |
| IAL-2 | OTP_VERIFIED | possession of registered OTP channel |
| IAL-3 | STRONG | OTP + trusted authenticator/device signature or biometric |
| IAL-4 | HIGH_ASSURANCE | strong multi-factor + regulated/TEE-backed proof |

The exact mapping is configurable in `AuthenticationPolicyService` and should ultimately come from bank security policy/configuration.

## Authentication flow

1. Client obtains/uses a `clientId` from client-identity-service.
2. Client starts an authentication transaction with a purpose and requested assurance.
3. Service creates a short-lived transaction in Redis and a durable audit/identity record in Oracle.
4. For OTP, a cryptographically random code is generated, hashed, stored only in Redis, and delivered by an `OtpDeliveryProvider`.
5. Client verifies the challenge. Attempts, expiry, purpose and transaction state are checked atomically at the service boundary.
6. A successful factor raises the achieved assurance level.
7. For step-up, another factor/provider can be required.
8. The service returns an `AuthenticationContext` containing `authenticationId`, `userId`, `clientId`, achieved assurance and method.
9. `token-service` can verify that context using the internal endpoint before issuing an access token.

## REST API

Base path: `/api/v1`

### User

`POST /users` create/register an identity.

`GET /users/{userId}` retrieve an identity.

`POST /users/{userId}/disable` disable an identity.

### Authentication

`POST /authentication/transactions` start an authentication transaction.

`GET /authentication/transactions/{authenticationId}` get current authentication state.

`POST /authentication/transactions/{authenticationId}/step-up` request stronger assurance.

`POST /authentication/transactions/{authenticationId}/revoke` revoke an authentication context.

### OTP

`POST /authentication/transactions/{authenticationId}/otp/challenge` issue an OTP challenge.

`POST /authentication/transactions/{authenticationId}/otp/verify` verify OTP.

### Biometric

`POST /authentication/transactions/{authenticationId}/biometric/verify` verify through the configured biometric provider.

The default provider is a **development mock**. Production mobile biometric integration should send a cryptographic assertion generated by a platform authenticator/TEE rather than raw face/fingerprint material.

### Internal token-service API

`POST /internal/v1/authentication-contexts/{authenticationId}/verify`

This endpoint verifies that an authentication context is valid, unexpired, not revoked, belongs to the expected user/client, and satisfies a required assurance level. Protect this endpoint with service-to-service authentication/mTLS in production.

## Example requests

Start login:

```json
{
  "userId": "user-123",
  "clientId": "cid-abc",
  "purpose": "LOGIN",
  "requiredAssuranceLevel": "IAL-2"
}
```

OTP verify:

```json
{
  "challengeId": "otp-...",
  "code": "123456"
}
```

Step-up to biometric:

```json
{
  "requiredAssuranceLevel": "IAL-3",
  "method": "BIOMETRIC"
}
```

Successful authentication context:

```json
{
  "authenticationId": "auth-...",
  "userId": "user-123",
  "clientId": "cid-abc",
  "purpose": "LOGIN",
  "authenticationMethod": "OTP",
  "assuranceLevel": "IAL-2",
  "authenticatedAt": "2026-09-08T14:00:00Z",
  "expiresAt": "2026-09-08T14:05:00Z"
}
```

## Redis vs Oracle

**Redis is for ephemeral security state:** OTP hashes, challenge state, counters, rate-limit windows and short-lived authentication transaction state.

**Oracle is the system of record:** user identity, authenticators, authentication transaction history, and security audit records.

Do not store raw OTP codes or raw biometric images in Oracle. Do not use Redis as the durable identity store.

## Provider extension points

The important interfaces are:

- `OtpDeliveryProvider`
- `BiometricProvider`
- `DeviceAssertionProvider` (future extension point)
- `AuthenticationPolicyService`

Production providers can be added without changing controllers or the transaction model.

## Database

Oracle schema migration scripts are intentionally included under `src/main/resources/db/migration` for teams that use Flyway later. The current module uses Hibernate `ddl-auto=validate` by default in production profile; for a fresh environment, run the supplied DDL first.

Main tables:

- `UI_USER_IDENTITY`
- `UI_AUTHENTICATOR`
- `UI_AUTH_TRANSACTION`
- `UI_AUTH_AUDIT`

See `src/main/resources/application.yml` and `application-dev.yml`.

Required production settings:

```text
ORACLE_URL
ORACLE_USERNAME
ORACLE_PASSWORD
REDIS_HOST
REDIS_PORT
```

Never commit real OTP delivery credentials, biometric provider credentials, Redis passwords or Oracle passwords.

## Add to bank-iot-platform parent

Add this line to the root `<modules>` list:

```xml
<module>user-identity-service</module>
```

Then:

```bash
mvn -pl user-identity-service -am clean verify
```

Run:

```bash
mvn -pl user-identity-service spring-boot:run
```

Default port: `8086`.

## Production hardening checklist

- Replace mock OTP delivery with the bank notification/SMS provider.
- Replace mock biometric provider with platform cryptographic assertion verification.
- Put service-to-service endpoints behind mTLS and/or signed service credentials.
- Move policy values to Spring Cloud Config/Vault when available.
- Use Vault for secrets; never put secrets in Git.
- Use Redis TLS/authentication and Oracle TLS.
- Add distributed rate limiting at gateway and service level.
- Use a transactional outbox if authentication events are later published to Kafka.
- Add fraud/risk engine integration before high-risk financial operations.
- Add transaction signing for high-value payments.
- Add WebAuthn/passkeys when required.
- Consider HSM/TEE-backed verification for IAL-4.

## Security design decision

The service does not put CID/DID verification logic into JWT issuance. `client-identity-service` establishes client trust, `user-identity-service` establishes human authentication, and `token-service` issues tokens after validating the resulting trusted authentication context. This keeps the three security domains independently evolvable.
